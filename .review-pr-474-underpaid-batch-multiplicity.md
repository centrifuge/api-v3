## Summary (top-level review body)

This PR replaces the single-row collapse for concurrent underpaid instances of the same batch with one payload row per gateway underpaid counter increment, and reworks the destination handle routing so deliveries no longer pin onto the lowest linked (usually completed) row. It directly fixes the pharos 2026-08-06 incident where the 4th underpaid send left no trace by tx-hash lookup.

Send side: `UnderpaidBatch` with a fresh unlinked `PrepareMessage` (`newSend`) now allocates `nextPayloadIndex` before the unsent-row fallback, matching the gateway counter semantics and the existing `SendPayload` rule. `HandlePayload` prefers the lowest open sent row that is not yet delivered, so each instance gets its own delivery.

Receive side: new pure `resolveHandleTargetIndex` with explicit precedence (unique adapter SEND participation, unique message linkage, FIFO over causally-possible open sent rows, lowest linked row as replay fallback). `resolvePayloadRowForHandle` now delegates to it instead of collapsing the message hint to the minimum index.

**What looks good**

- The per-instance model is the right call: facts are write-once (COALESCE), so a single row cannot hold two underpaid/repay/send/delivered tx-hash sets. The asymmetry with the paid `SendPayload` path (#465) is called out and removed.
- `resolveHandleTargetIndex` is extracted as a pure function with a clear precedence and thorough JSDoc. The causal filter (rows whose send anchor postdates the receive are excluded) is the right fix for the "stuck Delivered / completedAt null" staging symptom.
- Test coverage is strong: the pharos four-instance scenario is reproduced end-to-end, the `resolveHandleTargetIndex` matrix covers participation, linkage, FIFO, replay, and the causal-order edge. The three old collapse assertions were rewritten to the new model rather than deleted.
- No schema change; PK `(id, index)` and columns are untouched. The `MAX(index)+1` allocation composes with existing collapsed rows, so the fix is forward-safe without a forced reindex.

## Findings

### Design choices we're tracking (not blocking)

#### 1. Causal filter anchor falls back to underpaidAt for unsent rows

**Status:** Resolved. `resolveHandleTargetIndex` now filters to sent rows upfront, so unsent rows are never eligible and the causal anchor is always `sentAt`. The JSDoc reads accurately.

**File:** `src/services/CrosschainPayloadService.ts`
**Lines:** 430-440
**Also:** `src/helpers/crosschainReconciliation.ts` ~525-526

**GitHub comment:**

The causal filter uses `getPayloadSendAnchorAt` (`sentAt ?? underpaidAt`) as the per-row anchor. For a sent row this is `sentAt`, which is what the filter is for: a receive cannot belong to an instance sent after it. For an unsent underpaid row the anchor is `underpaidAt`, which is always <= the cross-chain delivery time, so unsent rows pass the filter and stay in the FIFO candidate set.

The JSDoc says "a receive cannot belong to a not-yet-sent instance", but the implementation only excludes rows sent after the receive, not unsent rows. This matches the old `HandlePayload` `open` fallback, so it is not a regression. Either tighten the filter to `sentAt` only (and let unsent rows fall through to the linked-row replay fallback), or adjust the JSDoc to "sent after the receive" so the contract reads accurately.

**Example:**

```
Row 0: underpaidAt=t0, sentAt=null (underpaid, awaiting repay)
Row 1: sentAt=t10, deliveredAt=null (in transit)
HandlePayload arrives at t8, linkedMessageIndices=[0,1], participationIndices=[]

causal filter (receivedAt=t8):
  row 0: anchor=underpaidAt=t0 <= t8 -> kept
  row 1: anchor=sentAt=t10 > t8 -> dropped
resolvePayloadKeyForEvent("HandlePayload", [row0], ...):
  openSent=[] (row0 not sent), open=row0 -> mutate index 0
-> returns 0; deliveredAt stamped on unsent row 0
```
